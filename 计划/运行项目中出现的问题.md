## 1. ECharts 首次进入统计页不渲染

### 现象
进入「支出统计」页面，API 数据正常返回（`recordCount > 0`），但饼图和柱状图区域空白，没有报错。

### 排查过程
1. 确认 API 返回数据正常 → 排除数据层问题
2. `console.log` 检查 `pieDom` / `barDom` → 均为 `null`
3. 发现问题：`<view id="pieChart">` 被 `v-if="loading"` 包裹，首次加载时 `loading=true`，DOM 元素不存在
4. `loading=false` 后调用 `renderCharts()`，但 `await nextTick()` 只等了一个微任务周期，Vue 的 DOM diff 还没完成，`id` 对应的元素还没挂载到 DOM 树上

### 根因
**Vue 的异步渲染队列**：`v-if` 切换后，DOM 插入发生在下一个宏任务（`setTimeout` 之后），而 `nextTick` 只保证响应式数据更新完成，不保证 DOM 已经 paint。

### 解决方案
```js
// ❌ 错误：nextTick 不够
await nextTick();
renderCharts(); // DOM 还没挂载，getElementById 返回 null

// ✅ 正确：setTimeout 推迟到下一个宏任务
await nextTick();
setTimeout(() => renderCharts(), 300); // 等待浏览器 paint 完成
```

### 其他可选方案
| 方案 | 实现 | 优缺点 |
|------|------|--------|
| `requestAnimationFrame` | `requestAnimationFrame(() => renderCharts())` | 比 setTimeout 更精确，但嵌套 v-if 可能仍需多次帧 |
| `MutationObserver` | 监听 DOM 插入后再初始化 | 太重，个人项目没必要 |
| `v-show` 替代 `v-if` | 元素始终在 DOM 中，只切换可见性 | 首次加载慢（隐藏元素也渲染），但省去初始化延迟 |
| Vue `ref` 模板引用 | `<view ref="pieRef">` + `pieRef.value` | **我们最终用了这个** + setTimeout 兜底 |

### 面试话术
> "在 uni-app 里集成 ECharts 遇到一个时序问题：页面用 `v-if` 控制加载状态，图表容器在 loading 结束后的 `nextTick` 里拿不到 DOM。原因是 Vue 的 DOM 更新是异步批量的，`nextTick` 在微任务队列执行，但 `v-if` 的元素真正插入 DOM 是在浏览器渲染之后。解决是用 `setTimeout(fn, 300)` 推迟到下一个宏任务，给浏览器足够的 paint 时间。同时也把 `getElementById` 换成了 Vue 的 `ref` 模板引用，更符合 Vue 的组件化思路。"

## 2. ECharts 切换月份后图表消失

### 现象
统计页首次进入正常渲染 ECharts 图表。切换到其他月份 → API 返回新数据 → 图表区域空白。再切回原月份 → 仍然是空白。

### 排查过程
1. API 数据正常 → 问题在渲染层
2. 加了 `console.log` 发现 `pieChart` 实例存在（不是 null），但 `setOption()` 不生效
3. 发现每次 `loading=true` 时 `v-if` 把 DOM 元素销毁了，`loading=false` 后重建了新 DOM
4. 但 `echarts.init()` 只在第一次创建了实例，后续复用了旧的、已绑定到被销毁 DOM 的实例
5. `pieDom`（新 DOM）≠ `pieChart` 内部持有的旧 DOM → `setOption()` 写到幽灵容器上了

### 根因
**ECharts 实例持有了对旧 DOM 的引用，Vue 的 `v-if` 销毁了旧 DOM 但 ECharts 实例不知道。** 切月份时 `loading` 状态切换 → 图表 DOM 被移除并重建 → 旧的 ECharts 实例变成"孤儿"（orphan instance），绑定的 DOM 已被 GC。

### 解决方案
```js
// ✅ 每次 load 前销毁旧实例
function destroyCharts() {
  if (pieChart) { pieChart.dispose(); pieChart = null; }
  if (barChart) { barChart.dispose(); barChart = null; }
}

async function load() {
  destroyCharts();        // ← 关键：先销毁，让实例变成 null
  loading.value = true;   // DOM 销毁
  // ... fetch data ...
  loading.value = false;  // DOM 重建
  await nextTick();
  setTimeout(() => renderCharts(), 300); // 用全新的 dom 创建新实例
}
```

### 其他可选方案

| 方案 | 实现 | 优缺点 |
|------|------|--------|
| `v-show` 替代 `v-if` | 不销毁 DOM，始终保留 | DOM 树始终存在，首次加载需渲染所有内容；但切换月份无闪烁 |
| 复用实例 + 手动绑定新 DOM | `pieChart?.dispose()` 后存旧 option 再 `init` 新 dom | 和销毁重建本质一样 |
| `watch` 监听 data 变化 | 数据变 → `setOption({...}, true)` 强制重绘 | 不解决 DOM 被销毁的问题，只适用 v-show |
| 把图表放外面不用 v-if 控制 | 始终渲染，loading 用绝对定位覆盖 | 最省事但 DOM 冗余 |

### 为什么选销毁重建
`v-if` + `dispose` + `init` 是最干净的方式——销毁时释放 ECharts 占用的 Canvas 内存、事件监听器和定时器。如果用 `v-show`，图表一直活着但隐藏状态仍消耗资源。对于页面有多个图表的场景，`dispose` 是最佳实践。

### 面试话术
> "切换月份后图表消失，排查发现是 Vue 的 `v-if` 和 ECharts 实例生命周期冲突。`v-if` 在切换状态时会销毁并重建 DOM，但 ECharts 实例持有了旧 DOM 的引用，新 DOM 上 `init` 的判断又因为实例不为 null 而跳过了初始化，导致 `setOption` 写入了一个已不存在的容器。解决方案是在每次数据加载前主动调用 `dispose()` 销毁旧实例，置 null，让下一轮 'init' 走全新创建路径。这也是 ECharts 官方推荐的做法——避免内存泄漏和幽灵渲染。"

## 3. 金额数字在汇总卡片中的居中对齐

### 现象
首页和三栏汇总卡片（本月收入 / 本月支出 / 结余）中，标题文字居中，但金额数字 `¥3000.00` / `¥620.00` / `¥2380.00` 视觉偏左，三条金额没有形成整齐的垂直对齐线。

### 排查过程
1. 外层容器 `summary-row` 用了 `display: flex; justify-content: center` — 这只是让三栏整体居中，不管栏内
2. 每个 `summary-item` 只有 `flex: 1` 等分宽度，没有设置 `text-align`
3. `summary-amount` 金额文本默认 `text-align: left`，数字长短不一 → 3000 vs 620 vs 2380 → 视觉左对齐参差
4. uni-app 的 `<text>` 组件默认是行内元素，`text-align` 不生效，必须加 `display: block`

### 根因
**两层对齐误区：**
1. **外层 flex 居中 ≠ 内容居中**：`justify-content` 控制的是 flex 子项在主轴的位置，不管子项内部的文本对齐
2. **`<text>` 组件的显示模式**：uni-app 的 `<text>` 默认是 `inline`，`text-align` 对行内元素无效

### 解决方案
```css
/* ❌ 错误 */
.summary-item { flex: 1; }
.summary-amount { font-size: 44rpx; } /* 默认 text-align: left */

/* ✅ 正确 */
.summary-item { flex: 1; text-align: center; }
.summary-label { display: block; }  /* text 标签变块级 */
.summary-amount { display: block; } /* text 标签变块级 */
```

### 其他方案

| 方案 | 实现 | 优缺点 |
|------|------|--------|
| `text-align: center` （我们用的） | 栏内全部居中 | 最简单，3 栏对称美观 |
| `text-align: right` + 等宽字体 | 财务风格，金额右对齐，小数点对齐 | 更专业但需要统一 padding |
| `justify-content: center` + `display: flex` 套一层 | 每栏内部也用 flex 居中 | 过度嵌套，不如 text-align |
| monospace 等宽字体 | `font-family: monospace` | `¥` 符号不算等宽，数字对齐了但符号不齐 |

### 面试话术
> "三栏汇总卡片的金额视觉歪了，排查发现两个问题：一是只给外层 flex 容器设了居中，但栏内文本没有 `text-align: center`；二是 uni-app 的 `<text>` 组件默认 inline，`text-align` 不生效，需要设 `display: block`。修起来就两行 CSS，但踩这个坑让我理解了 flex 布局的作用域——`justify-content` 管的是子项排列，不管子项内部的文本。后面做类似布局都会先确认对齐是在哪个层级生效的。"

## 4. uni-app H5 原生 `<input>` 无法输入

### 现象
登录页表单中，按钮可以点击，但输入框完全无法获取焦点——点击输入框没有光标、键盘不弹出。控制台无任何报错。

### 排查过程
1. 去掉 `:disabled`、`isLoading`、`@confirm` 等所有 JS 逻辑 → 仍无法输入
2. 去掉所有 CSS（动画、媒体查询、box-sizing、transition）→ 仍无法输入
3. 使用浏览器 DevTools 检查 input 元素 → DOM 存在、没有 `pointer-events: none`、没有被遮挡
4. 切换到 `uni-easyinput` 组件 → 立刻恢复正常

### 根因
uni-app H5 模式下，原生 `<input>` 标签在某些布局条件下（flex 居中 + border-radius + box-sizing 组合）存在点击热区计算偏移的 bug。浏览器端 `<input>` 实际上是原生 HTML input，但 uni-app 的编译管线会在外面包裹一层 `<uni-input>` 容器，容器的 `display: inline-block` + flex 父元素的居中计算会导致实际可点击区域与视觉区域错位。这个 bug 在 uni-app 2.x/3.x 均有出现，官方建议表单场景使用 `uni-easyinput` 替代。

### 解决方案
```vue
<!-- ❌ 不推荐：uni-app H5 原生 input 可能无法聚焦 -->
<input v-model="username" placeholder="用户名" />

<!-- ✅ 推荐：uni-easyinput 是官方封装，处理了多端兼容 -->
<uni-easyinput v-model="username" placeholder="用户名" :input-border="true" />
```

### 其他方案
| 方案 | 优缺点 |
|------|--------|
| `uni-easyinput`（已采用） | uni-ui 内置，无需额外依赖，和项目现有组件一致 |
| 外层套 `<view>` + `@click` 手动 `focus()` | hack，每个 input 都要写 ref 和 focus 逻辑 |
| 改用 `type="text"` 的 `<u-input>` | uView UI 的组件，但项目已用 uni-ui，不需要另外引入 |
| 等 uni-app 官方修复 | 不现实，这个 bug 存在多个大版本了 |

### 面试话术
> "在 uni-app H5 端遇到原生 input 无法获取焦点的 bug，排查了很久——去掉 disabled、去掉所有 CSS、检查 DOM 遮挡都没找到原因。最后发现是 uni-app 编译管线在 H5 模式下对原生 input 的包裹容器有布局计算偏差，导致点击热区和视觉区域错位。换成 uni-app 官方封装的 'uni-easyinput' 就解决了。这个坑让我理解了为什么跨端框架都有自己的组件封装层——直接写 HTML 标签在单端可能没问题，多端就会有各种奇怪的兼容性问题。"

## 5. 弹窗保存按钮被 TabBar 遮挡

### 现象
记账弹窗从底部弹出后，"保存账单"按钮被手机底部的 TabBar（首页/账单/我的）完全遮挡，用户无法点击保存。PC 端和手机端都有这个问题。

### 排查过程
1. 弹窗设置了 `max-height: 75vh`，看似留了 25vh 空间
2. 但 TabBar 高度约 100rpx（50px），加上弹窗自身的 padding 和按钮高度，实际占用超过 25vh
3. 弹窗内容过多时，底部按钮被挤出可视区域，被 TabBar 遮挡
4. 用户看不到按钮，以为功能失效

### 根因
**弹窗高度计算未考虑 TabBar 占用**：`75vh` 只是视口高度的 75%，但 TabBar 是固定在底部的原生组件，会遮挡弹窗内容。uni-app 的 `vh` 单位包含 TabBar 区域，需要额外预留空间。

### 解决方案
```css
/* ❌ 错误：75vh 太高，按钮被 TabBar 遮挡 */
.popup-wrapper {
  max-height: 75vh;
}

/* ✅ 正确：减少到 60vh，为 TabBar 预留足够空间 */
.popup-wrapper {
  max-height: 60vh;
}
```

### 其他方案
| 方案 | 优缺点 |
|------|--------|
| 减少弹窗高度（已采用） | 简单直接，兼容所有端 |
| 使用 `calc(100vh - 200rpx)` | 更精确，但 rpx 在不同设备上换算复杂 |
| 给按钮添加 `margin-bottom: 100rpx` | 按钮可见但弹窗底部留白过多，不美观 |
| 隐藏 TabBar 当弹窗打开时 | 需要修改全局状态，影响其他页面 |

### 面试话术
> "弹窗保存按钮被 TabBar 遮挡，排查发现是 `vh` 单位计算误区——`75vh` 包含了 TabBar 占用的高度，弹窗实际可用空间不足。解决方案是减少弹窗最大高度到 `60vh`，为 TabBar 预留足够空间。这个坑让我理解了移动端布局的特殊性——`vh` 不是简单的视口百分比，还要考虑原生组件（TabBar、状态栏）的遮挡。"

## 6. PC 端日历弹窗无法滚动

### 现象
PC 端点击日期选择器，日历弹窗弹出后，右侧出现滚动条但无法拖动，也无法用鼠标滚轮下滑。手机端正常。

### 排查过程
1. 日历弹窗使用了 `position: fixed`，层级 `z-index: 9999`
2. 弹窗内容高度超过屏幕高度，出现滚动条
3. 但滚动条无法交互，鼠标滚轮也无效
4. 检查发现弹窗被包裹在 `scroll-view` 组件内，`overflow-y: auto` 导致滚动事件被拦截

### 根因
**scroll-view 的滚动事件拦截**：uni-app 的 `scroll-view` 组件会捕获内部的所有滚动事件，包括 fixed 定位的子元素。日历弹窗虽然 `position: fixed`，但仍然在 `scroll-view` 的 DOM 树内，滚动事件被 `scroll-view` 拦截，导致日历自身无法滚动。

### 解决方案
```vue
<!-- ❌ 错误：scroll-view 拦截了日历的滚动事件 -->
<scroll-view class="popup-scroll" scroll-y>
  <uni-datetime-picker v-model="formDate" type="date" />
</scroll-view>

<!-- ✅ 正确：给日历弹窗添加自己的滚动容器 -->
<scroll-view class="popup-scroll" scroll-y>
  <uni-datetime-picker v-model="formDate" type="date" />
</scroll-view>

<style>
/* 给日历弹窗添加独立的滚动 */
:deep(.uni-calendar__content) {
  max-height: 60vh;
  overflow-y: auto;
}
</style>
```

### 其他方案
| 方案 | 优缺点 |
|------|--------|
| 给日历内容区域添加 `overflow-y: auto`（已采用） | 日历自己处理滚动，不受 scroll-view 影响 |
| 把日历移到 scroll-view 外面 | 破坏组件结构，不适合表单场景 |
| 使用原生 `<input type="date">` | 样式不统一，手机端体验差 |
| 禁用 scroll-view 的滚动 | 弹窗内容无法滚动，更糟 |

### 面试话术
> "PC 端日历弹窗无法滚动，排查发现是 uni-app 的 `scroll-view` 组件会捕获内部所有滚动事件，包括 `position: fixed` 的日历弹窗。解决方案是给日历内容区域单独添加 `overflow-y: auto`，让它自己处理滚动，而不是依赖外层容器。这个坑让我理解了滚动事件的冒泡机制——即使元素是 fixed 定位，只要在 scroll-view 的 DOM 树内，滚动事件就会被拦截。"

## 7. 表单验证错误提示不可见

### 现象
用户在填写记账表单时，如果金额输入错误（比如 0 或负数），点击保存后，错误提示出现在弹窗顶部。但用户通常在弹窗底部（刚填写完日期），看不到顶部的错误提示，以为保存成功但没有反应。

### 排查过程
1. 错误提示 `<view v-if="formError" class="form-error">` 在弹窗顶部
2. 用户填写表单时，焦点在底部的日期选择器
3. 点击保存后，错误提示出现在顶部，但用户视野在底部
4. 用户看不到错误提示，反复点击保存按钮，以为功能失效

### 根因
**错误提示位置与用户视野不匹配**：弹窗内容可以滚动，用户填写表单时滚动到底部，但错误提示固定在顶部，不在用户当前视野内。用户看不到错误提示，无法得知保存失败的原因。

### 解决方案
```js
// ✅ 出现错误时自动滚动到顶部，让用户看到错误提示
async function submitBill() {
  formError.value = '';
  const amount = parseFloat(formAmount.value);
  
  if (isNaN(amount) || amount <= 0) { 
    formError.value = '请输入大于 0 的有效金额'; 
    scrollToTop(); // 关键：滚动到顶部显示错误
    return; 
  }
  
  // ... 保存逻辑 ...
}

function scrollToTop() {
  scrollTop.value = 0;
  setTimeout(() => {
    scrollTop.value = 0.1; // 强制触发滚动
  }, 50);
}
```

```vue
<!-- scroll-view 绑定 scroll-top 属性 -->
<scroll-view 
  class="popup-scroll" 
  scroll-y 
  :scroll-top="scrollTop"
  :scroll-with-animation="true"
>
  <!-- 表单内容 -->
</scroll-view>
```

### 其他方案
| 方案 | 优缺点 |
|------|--------|
| 错误时滚动到顶部（已采用） | 用户立即看到错误提示，体验最好 |
| 错误提示改为 Toast | 简单但提示时间短，用户可能错过 |
| 错误提示跟随视野移动 | 复杂，需要监听滚动事件 |
| 在按钮附近显示错误 | 按钮固定在底部，空间有限 |

### 面试话术
> "用户反馈保存按钮点击没反应，排查发现是错误提示在弹窗顶部，但用户视野在底部，看不到提示。解决方案是在表单验证失败时，用 `scroll-view` 的 `scroll-top` 属性自动滚动到顶部，让错误提示进入用户视野。这个坑让我理解了表单设计的细节——错误提示不仅要显示，还要确保用户能看到。好的用户体验是主动引导用户注意到错误，而不是让用户自己去找。"

## 8. 移动端弹窗被 TabBar 遮挡的终极方案

### 现象
记账弹窗从底部弹出后，无论怎么调整 `max-height`（75vh → 65vh → 60vh），"保存账单"按钮始终被手机底部的 TabBar 遮挡。PC 端正常，手机端按钮只显示一半。

### 排查过程
1. 第一次尝试：`max-height: 75vh` → 按钮被遮挡
2. 第二次尝试：`max-height: 65vh` → 按钮仍被遮挡
3. 第三次尝试：`max-height: 60vh` → 按钮还是被遮挡
4. 发现问题：vh 单位包含 TabBar 区域，单纯减少高度不是根本解决方案
5. 最终方案：弹窗打开时直接隐藏 TabBar

### 根因
**TabBar 是原生组件，会遮挡弹窗内容**。uni-app 的 TabBar 是固定在底部的原生导航栏，不是普通的 DOM 元素，无法通过 CSS 的 z-index 或 margin 来避开。`vh` 单位计算的是整个视口高度，包括 TabBar 占用的区域。

### 解决方案
```js
// ✅ 弹窗打开时隐藏 TabBar，关闭时恢复
function openPopup() { 
  popupRef.value.open();
  // #ifndef H5
  uni.hideTabBar(); // 隐藏 TabBar，释放底部空间
  // #endif
}

function closePopup() { 
  popupRef.value.close();
  // #ifndef H5
  uni.showTabBar(); // 恢复 TabBar
  // #endif
}

// 监听弹窗状态变化，确保 TabBar 恢复
function onPopupChange(e) {
  if (!e.show) {
    // #ifndef H5
    uni.showTabBar();
    // #endif
  }
}
```

```css
/* 弹窗可以使用更多空间 */
.popup-wrapper {
  max-height: 70vh; /* TabBar 隐藏后，可以用更多空间 */
}
```

### 为什么不选其他方案
| 方案 | 为什么不选 |
|------|-----------|
| 继续减少 vh（60vh → 50vh） | 弹窗内容太少，用户体验差 |
| 给按钮加 margin-bottom | 弹窗底部留白过多，不美观 |
| 用 position: fixed 覆盖 TabBar | TabBar 是原生组件，无法覆盖 |
| 隐藏整个页面的 TabBar | 影响其他页面，状态管理复杂 |

### 面试话术
> "弹窗按钮被 TabBar 遮挡，我试了三次调整 vh 高度（75→65→60）都没解决，最后发现 TabBar 是原生组件，会遮挡弹窗内容。终极方案是弹窗打开时调用 `uni.hideTabBar()` 隐藏 TabBar，关闭时恢复。这样不仅解决了遮挡问题，弹窗还能用更多空间（70vh），用户体验更好。这个坑让我理解了移动端布局的特殊性——原生组件（TabBar、状态栏）和 Web 内容是两个层级，需要用 API 而不是 CSS 来控制。"

## 9. 日期选择器的跨端统一方案

### 现象
PC 端使用 `uni-datetime-picker` 组件，但出现两个问题：1）日历弹窗被外层 `scroll-view` 裁剪无法滚动；2）手机端日历弹窗位置不对，被 TabBar 遮挡。

### 排查过程
1. PC 端：日历弹窗有滚动条但无法滚动，是 `scroll-view` 拦截了滚动事件
2. 手机端：日历弹窗位置太高，与 TabBar 重叠
3. 尝试给日历弹窗添加 `position: fixed` + `z-index: 9999` → PC 端可以滚动但位置仍不对
4. 尝试给日历内容区域添加 `overflow-y: auto` → PC 端可以滚动但手机端仍有遮挡
5. 最终方案：PC 和手机统一使用 `<picker mode="date">` 原生下拉选择器

### 根因
**uni-datetime-picker 是自定义组件，多端兼容性差**。它的弹窗是从组件内部弹出的，会受到外层容器（如 `scroll-view`）的样式影响。不同端（H5/小程序/App）的渲染机制不同，导致位置计算和滚动行为不一致。

### 解决方案
```vue
<!-- ❌ 不推荐：uni-datetime-picker 多端兼容性差 -->
<uni-datetime-picker v-model="formDate" type="date" />

<!-- ✅ 推荐：picker 原生组件，多端统一 -->
<picker mode="date" :value="formDate" @change="onDateChange" class="date-picker-mobile">
  <view class="picker-display">
    <uni-icons type="calendar" size="16" color="#64748b" />
    <text class="picker-text">{{ formDate }}</text>
  </view>
</picker>
```

```js
// 日期选择回调
function onDateChange(e) {
  formDate.value = e.detail.value;
}
```

```css
/* 自定义 picker 显示样式 */
.picker-display {
  display: flex;
  align-items: center;
  gap: 12rpx;
  background: #f8fafc;
  border: 2rpx solid #e2e8f0;
  border-radius: 16rpx;
  padding: 24rpx 28rpx;
  transition: border-color 0.2s ease;
}

.picker-display:active {
  border-color: #10b981;
}
```

### 为什么 picker 更好
| 特性 | uni-datetime-picker | picker |
|------|-------------------|--------|
| 跨端兼容性 | 差（H5/小程序表现不一致） | 好（原生组件，统一） |
| 样式定制 | 复杂（需要 deep 选择器） | 简单（只需包装一层 view） |
| 滚动问题 | 有（被 scroll-view 拦截） | 无（原生下拉，不受容器影响） |
| 位置问题 | 有（弹窗位置计算错误） | 无（从底部弹出，固定位置） |
| 代码复杂度 | 高（需要处理各种边界情况） | 低（几行代码搞定） |

### 面试话术
> "日期选择器在 PC 端和手机端表现不一致，PC 端日历无法滚动，手机端日历被 TabBar 遮挡。我尝试了各种 CSS 修复（z-index、overflow、position），都没根本解决。最后统一改用 uni-app 的 `<picker mode="date">` 原生组件，问题全没了。这个坑让我理解了跨端开发的原则——优先使用原生组件，它们经过了充分的多端测试；自定义组件虽然功能强大，但兼容性难以保证。"

## 10. 组件抽离后的样式冲突问题

### 现象
将表单组件抽离成公共组件（TypeToggle、CategoryGrid）后，PC 端的日期选择器点击无反应，只有滚动条。手机端正常。

### 排查过程
1. 抽离前：日期选择器正常工作
2. 抽离后：PC 端日期选择器点击无反应
3. 检查 z-index：都设置了 9999
4. 检查 overflow：scroll-view 有 overflow-y: auto
5. 发现问题：抽离后组件的 scoped 样式影响了全局样式优先级

### 根因
**scoped 样式的优先级问题**。抽离组件后，原有的全局样式（如 `.uni-date__popup` 的 z-index）被组件的 scoped 样式覆盖或失效。Vue 的 scoped 样式会给元素添加 `[data-v-xxx]` 属性选择器，优先级高于普通全局样式。

### 解决方案
```css
/* ❌ 错误：scoped 样式可能覆盖全局样式 */
<style scoped>
.date-picker {
  z-index: 10;
}
</style>

/* ✅ 正确：使用 :deep() 确保全局样式生效 */
<style scoped>
:deep(.uni-date__popup),
:deep(.uni-calendar__popup) {
  position: fixed !important;
  z-index: 9999 !important;
}
</style>
```

或者更简单：**统一改用 picker 原生组件**，避免样式冲突。

### 面试话术
> "组件抽离后，日期选择器在 PC 端失效了。排查发现是 scoped 样式的优先级问题——抽离组件后，全局样式被 scoped 样式覆盖。解决方案是用 `:deep()` 选择器穿透 scoped 样式，或者干脆改用原生 picker 组件。这个坑让我理解了 Vue 样式隔离的代价——scoped 样式虽然避免了冲突，但也增加了调试难度。"
